# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`rush` is a POSIX-style shell in Rust (edition 2024), being ported from an earlier C++ implementation. Several files still carry the original C++ in comments (e.g. the top of `src/waiter.rs`, blocks in `src/executor.rs`) as the reference for what the Rust code must do. Job control follows the GNU libc manual's "Implementing a Shell" design (linked from `src/job.rs`).

The port is mid-way: simple commands, pipelines, `;`/`&&`/`||`/`!` lists, `&`, subshells, `if`, command substitution, quoting, parameter expansion (variables, special and positional parameters, `"$@"` fields, the `${x:-y}` operators), redirections, `VAR=x` prefixes and assignments run end to end; the shell reads stdin, a script (`rush script args`) or `-c string`. Built-ins: `cd`, `pwd`, `exec`, `eval`, `:`, `true`, `false`, `exit`, `jobs`, `fg`, `bg`, `export`, `readonly`, `unset`, `set` (not its options), `shift` and `help` (not POSIX, like bash's) work, the other POSIX built-ins are stubs (`rush: <name>: not implemented yet`, status 1). Expect dead-code warnings.

Code style: the order of items in a `.rs` file (type definitions on top, `impl`s and functions below, tests last) is in the `rust-file-layout` skill (`.claude/skills/rust-file-layout/SKILL.md`).

Porting progress is tracked in `TODO.md` (sections mirror the C++ sources); the built-ins have their own plan and per-built-in checklist in `BUILTINS.md`. Tick items there as they are completed.

The POSIX spec (Issue 7, 2018) is kept locally in `docs/`: the Shell Command Language (§2, incl. §2.14 special built-ins) in `docs/The Open Group Base Specifications Issue 7, 2018 edition_files/mindex.html`, one page per regular built-in in `docs/utilities/<name>.html`. The parser's doc comments quote its BNF; the built-ins link their spec page.

## Commands

```sh
cargo check            # fastest feedback; the main verification step
cargo build
cargo run              # interactive REPL on stdin; parser dumps the syntax tree to stderr
cargo clippy
cargo test                             # unit tests + end-to-end tests
cargo test --test redirections <name>  # one end-to-end test (files in tests/, one per feature)
cargo test --test builtins cd::        # one built-in's tests (tests/builtins/)
cargo test --bin rush                  # only the unit tests inside src/
cargo fmt
printf 'echo hi | tr a-z A-Z\n' | cargo run -q 2>/dev/null   # quick manual check
```

Dependencies: `libc` (raw syscalls), `regex` (tokenizer) and `clap` (argument parsing and help text of the built-ins, with the `string` feature for runtime command names).

End-to-end tests run the binary and live in `tests/`, one file per feature (`repl`, `invocation`, `quoting`, `parameters`, `commands`, `compound_commands`, `pipelines`, `lists`, `subshells`, `async_lists`, `substitutions`, `redirections`, `environment`, `job_control`); put new tests in the file of the feature they exercise, or add a file for a new feature. Built-in tests are in `tests/builtins/`, one module per built-in (`cd.rs`, …), compiled as the single `builtins` target through `tests/builtins/main.rs`: it pulls in the helpers with `#[path = "../common/mod.rs"] mod common;`, modules import them as `crate::common`, and a new built-in's tests need a `mod <name>;` line there. `tests/builtins/not_implemented.rs` lists the stubs: remove a name once it is implemented. Shared helpers are in `tests/common/` (each test file declares `mod common;`):
- `common/mod.rs`: the shell non-interactive, input on a piped stdin, assertions on stdout/stderr (`run_shell`, `run_shell_in` + `test_dir` for tests that touch files). stderr also carries the syntax tree dump, which contains the command's tokens: assert on the program's own message, not on words from the command line.
- `common/pty.rs`: `InteractiveShell`, the shell on a pty as the leader of its own session. Echo is off, so stdout holds only what commands print; stderr is a separate pipe. Wait for state with `expect`/`expect_prompt`/`wait_foreground_job` (`wait_foreground_process` when the program is not the group leader, e.g. inside a subshell), never with sleeps. `job_control.rs` checks process groups and terminal ownership through `/proc/<pid>/stat` and `tcgetpgrp` on the master.

To poke at interactive mode by hand: `script -qec target/debug/rush /dev/null`.

## Architecture

Pipeline: `main` parses the shell's arguments (`Invocation`) → `Executor::start` → input lines (stdin, a script read whole, or the `-c` string) → `Executor` → `BufTokenizer` → `SyntaxTree` (parser) → `Executor` walks the AST and spawns processes → `Job` → `Waiter`.

- **`tokenizer.rs`**: regex-driven tokenizer following POSIX §2.3; the token text is capture group 1 of each spec (a trailing context, like the `<`/`>` after an `IO_NUMBER`, is outside it). There are three spec tables, one per `Mode`: `Normal`, `SingleQuoted`, `DoubleQuoted`; the parser picks the mode (`next_token_in`, `peek_in`, `next_if_type_in`; the plain methods are `Normal`). In `Normal` mode blanks (space, tab) and comments are skipped; a `#` starts a comment only at the start of a token (`a#b` and `'a'#b` are words). A word is not one token: it is a run of glued parts (`Literal`, `SQuote` + `SqText` + `SQuote`, `DQuote` + `DqText`/`Param`/`ParamOpen`/`Andopen`/`Backquoted` + `DQuote`, `Param`, `ParamOpen` ... `CloseBrace`, `Andopen` ... `CloseRound`, `Backquoted`); `Token::glued` says no blank came before it on the line. `Literal` takes every character but blanks, newline, operators and quoting characters (`* ? [ ] ~ { } ! €` are word characters); `Bang` is `!` only as a word of its own; `Param` is `$name` with the longest name (Unicode, like `is_valid_name`), `$0`–`$9` and the special parameters, each complete in itself (`NAME`/`SPECIAL` are the shared patterns). Of `${...}` the tokenizer only recognizes the opening (`ParamOpen`, §2.3 rule 5): the parser reads the rest, asking for each piece in its own mode: `Mode::ParamName` (`ParamHash`, the `#` of a length, then `ParamName`), `Mode::ParamOp` (`ParamOp` or `CloseBrace`), then the word in `Mode::ParamWord` (like `Normal`, but blanks are text and only `}` ends it) or `Mode::ParamWordDq` inside double quotes (where `'` is text). `Token::text()` removes the escapes of its context (unquoted, `\x` → `x`; inside double quotes only before `$`, a backquote, `"`, `\` and a newline; nothing inside single quotes). `UnbufferedTokenizer` works on one line, `BufTokenizer` spans the multi-line input buffer, in any mode (a quote can span lines). Both implement the `Tokenizer` trait with interior mutability (`Cell`/`RefCell`), so parser functions take `&T` and backtrack by cloning the tokenizer and calling `merge` on success.
- **`syntax.rs`**: recursive-descent parser. Each `SyntaxTree::<rule>` fn corresponds to a production of the POSIX shell grammar, with the BNF in its doc comment. They return `Option<Node>` (`None` = rule didn't match). AST nodes borrow from the input (`'a` lifetime on `Token<'a>`). A `Word` is a list of `WordPart`s (`Literal`, `SingleQuoted`, `DoubleQuoted(parts)`, `Param`, `CmdSub`, `Backquoted`) that `SyntaxTree::word` reads while the next token is glued; A parameter expansion is `WordPart::Param(ParamExpansion { param, braced, op })`, read by `SyntaxTree::param_expansion` (in the mode of its context): `param` is a `Parameter` (`Name`, `Positional`, `Special(Special)`, built by `Parameter::from_name` from the lexed name), `op` an optional `ParamOp` (`Length`, `Default`/`Assign`/`Error`/`Alternative` with `colon` and their `word`, `RemoveSuffix`/`RemovePrefix` with `largest` and their `pattern`), whose word `param_word` parses up to the `}` like any word (quotes, `$(...)`, nested `${...}`). Like dash, a `${...}` that doesn't parse (`${}`, `${a b}`, no `}`) is a syntax error of the whole input, also inside a branch that would never run. `AssignmentWord { key, value: Word }` is a word whose first part is unquoted text with `name=` (rule 7b), the rest is the value. Redirection targets are words too: `FileRedirect.filename`, and `Redirect::Dup { fd, output, target }` for `<&`/`>&` (a number or `-` after expansion). `Display` prints the AST back with the raw text of the words. The functions follow the order of the grammar in the spec (§2.10.2, "The Grammar" in `mindex.html`; `cmdsub` first, the `word`/`assignment_word` terminals and helpers last): keep that order when adding one. Reserved words (§2.4, the `ReservedWord` enum, named like the grammar's terminals) are not tokens: a word is one when it is a single unquoted `Literal` with that text (`syntax::reserved`, through `ReservedWord::parse`). `cmd_name` refuses them (rule 7a), so `then` ends the condition of an `if`, while after a prefix (`cmd_word`, rule 7b) and as arguments they are ordinary words; the grammar's `If`/`Then`/`Fi`... are matched by `SyntaxTree::reserved_word(tok, ReservedWord::Then)`. A compound command is `Command::Compound { command: CompoundCommand, redirections }` (`Subshell` or `If`), the `redirect_list` after it kept apart from the command; `IfClause` has its `else_part`, an `ElsePart::Elif(ElifClause)` (with its own `else_part`) or `ElsePart::Else(ElseClause)`. The rules not parsed yet (compound commands `for`/`case`/`while`/`until`/`{ }`, whose reserved words are already syntax errors where a command starts, function definitions, here-documents, `sequential_sep`) are `unimplemented!` stubs with their BNF, returning `()` where the AST node doesn't exist yet; nothing calls them yet (calling one would panic), see the TODOs in `command` and `compound_command`.
- **`executor.rs`**: REPL loop (prompt, line continuation via trailing `\`, `&&`, `||`, `|`; lines come from `Input`: stdin, or the lines of a script; `start` runs a `-c` string with `execute_str` and returns `$?` as the exit status) and AST evaluation. Programs are spawned with `std::process::Command`; shell code that needs its own process (subshell, `&`, `$(...)`) is run by `fork_child`: `nix::fork`, the child sets itself up (`enter_child`: process group, terminal, signals per `SpawnType`, stdin/stdout, redirections; `SpawnType::CmdSub` is not a job: it stays in the shell's group with SIGTSTP/SIGTTIN/SIGTTOU still ignored, since the shell reads all of its output before waiting and a stopped `$(...)` would hang it), drops job control (`is_interactive = false`, `pgid = getpgrp()`; it keeps a snapshot of the job table, so `jobs | cat` works, but can't wait on those jobs), runs the body under `catch_unwind` and ends in `nix::_exit`. Unlike `Command::spawn`, `fork` returns before the child ran, so the parent repeats `setpgid`/`tcsetpgrp`. Redirections are prepared in the parent by `RedirectController` (opens the files, checks `n>&m` fds, so errors are reported before spawning) into an ordered list of `RedirectOp`s, applied left to right in the child through `pre_exec` using a raw-pointer `RedirectionApplyer` that is freed right after `spawn`. The fds the shell creates for a command (the opened files, close-on-exec, and the copies `RedirectGuard` saves) go above the highest fd the redirections name (`RedirectController::floor`), so a redirection can't overwrite a file a later one still needs, and they never take a number the user wrote. `n>&m` only accepts an `m` the command opened earlier or one the user has open: not the shell's own fds (`Shell::internal_fds`, the terminal copy). `expand_fields` expands a `Word` into fields and removes the quotes, through a `Fields` builder (`keep`: the field holds quoted text, so it stays when empty): `"$@"` and unquoted `$@`/`$*` give a field per positional parameter, glued to the text around them, `"$@"` with none gives no field, and an unquoted expansion that gives nothing removes its field (`cmd $EMPTY`; no IFS splitting or pathname expansion yet). `expand_text` is for assignment values (no fields: `$@` joined by spaces). `expand_parameter` applies a `ParamExpansion`: the value comes from `Shell::parameter` (`None` when unset), the operators decide (§2.6.2; their words are expanded only when used, into the same `Fields`), and inside double quotes an expansion keeps its field even when empty, but `"$@"` with no parameters. The patterns of `%`/`#` are expanded by `expand_pattern` (quoted characters escaped with `\`, so they match themselves) and matched by `pattern::Pattern`. An expansion that can't be done (`${x?}`, `${1=x}`, a readonly `${x=y}`) is an `ExpansionError`, returned by `expand_fields`/`expand_text` up to the command. An error that stops a command before it runs is a `CommandError` (`Expansion`, `Assignment` for a readonly variable, `Redirect`; `expand_redirects` returns one, an expansion or a redirection error), reported by `command_error`, which carries out the §2.8.1 consequence: an expansion or assignment error exits a non-interactive shell, a redirection error only on a special built-in, and never for a command of a pipeline (`in_child`: it has a subshell environment of its own, only it fails; `Executor::exits`). `fail` prints and exits or gives 1; `builtin_error` does the same for a built-in's own error. They are marked to be replaced by the application's error handler (TODO.md §10). `$(...)` and backquotes go through `command_output`, which records the status in `cmdsub_status`: a command without a command name (`X=$(false)`, or words that expand to nothing, run by `assignments`) has the status of its last command substitution. `$?` (`Shell::last_status`) is set at the end of `wait_pipeline`, to 0 by `async_list` (which also sets `$!`) and to 2 on a syntax error; `expand_redirects` turns the AST `Redirect`s into `Redirection`s (`File`/`Dup`/`Close`, the target expanded; a `>&` target that is not an fd or `-` is a `RedirectError::BadTarget`), which is what `RedirectController::from_redirects` takes. A compound command (`Executor::compound`) is forked when it is a subshell or part of a pipeline (`fork_child` with `SpawnType::Subshell`, the child runs `compound_body`); the others run in the shell process (`compound_body`), so their assignments and `cd` stay, their redirections applied by a `RedirectGuard` (`RedirectGuard::open`) like a built-in's. A redirection error on it only fails it, like in dash and bash (§2.8.1: "may exit"). `if_clause`/`conditional` run the conditions in order, the status is the one of the part that ran, 0 when none did, and a condition interrupted by SIGINT stops it. Shell code run without a process of its own gives its pipeline a `JobExit` through `job_exit`. `unsub_command` expands the words, the prefixes and the redirections into a `SimpleCommand` (defined in `executor.rs`), then looks the program up in `builtin::BUILTINS`: a built-in runs in the shell process (`run_builtin`), or in a forked child (`fork_child`) when it is part of a pipeline of more than one command, anything else is spawned (`simple_command`). Each command gets a `PipelineState`: its stdin, where its stdout goes (`Output::Inherit`/`Pipe`/`Fd`), `in_pipeline` (the pipeline has more than one command, decided once by `schedule_pipeline`: built-ins are then forked and assignments skipped, whatever the command's position), the foreground flag and the job's pgid. Each command of a pipeline returns a `CommandRun`: `Spawned` (pid, the pgid it ended up in, and the read end of its output pipe inside a pipeline) or `Done(JobExit)` for a command that finished without a process (an assignment, or a spawn/redirection failure: 127/126/1, error already printed). The child's environment is built from scratch (`set_command_env`: `env_clear`, `ShellEnv::exported()`, then the command's `VAR=x` prefixes). A bare assignment goes through `ShellEnv::assign` (kept exported if it was; a readonly variable is an assignment error), and is a no-op inside a pipeline. `schedule_pipeline()` builds a `Job` via `JobBuilder`, and the **last command of the pipeline becomes the `job_master`**, whose status is the job's exit status (`JobMaster::NotSpawned` when it failed to spawn).
- **`invocation.rs`**: the shell's own arguments (`sh` in XCU), parsed by hand into an `Invocation`: the `Source` (`Stdin`, also with `-s`; `Command` for `-c string`; `Script`), `$0` (argv[0], the script path, or the name after the `-c` string), the positional parameters, and the option letters / `-o name`, applied through `Shell::set_option` (refused unless they change nothing). A bad invocation prints the usage and exits with 2. A script is read whole into lines (`Input::script`: 127 when it doesn't exist, 126 when it can't be read), so no fd of the shell's can be clobbered by a redirection; with `-c` or a script the shell is never interactive.
- **`nix.rs`**: a small hand-rolled subset of the `nix` crate on top of `libc`: `Pid` newtype, `Signal` enum (discriminants are the real `libc::SIG*` values, so `sig as c_int` is valid), `waitpid` returning `WaitRes`, and `close`/`dup2`/`kill`/`isatty`/`getpgrp`/`setpgid`/`tc{get,set}attr`/`tc{get,set}pgrp` wrappers, and `signal()` (via `sigaction`, async-signal-safe so usable in `pre_exec`). Syscall results go through `cvt()` (`-1` → `io::Error::last_os_error()`). User-facing error messages use `nix::error_message(&err)` (plain `strerror` text, without the `(os error N)` suffix of `io::Error`'s `Display`). Add new syscall wrappers here rather than calling `libc` directly elsewhere.
- **Variable names and values are UTF-8**, not only ASCII: a name is a Unicode letter or `_`, then Unicode letters, digits and `_` (`syntax::is_valid_name`, the one check used by the parser for `name=value` and by the built-ins for their operands; POSIX only requires the portable character set). Values are `String`s; environment entries that aren't valid UTF-8 are skipped (`ShellEnv::from_env`). Keep both in mind for anything that reads, prints or quotes variables.
- **`pattern.rs`**: the pattern matching notation (§2.13.1), for `${x%pattern}` and the like now, `case` and pathname expansion later. `Pattern::new` parses `*`, `?`, bracket expressions (`!`/`^`, ranges, `]` first, the `[:class:]`es) and `\` quoting (an invalid `[` matches itself); `matches` works on `char`s with backtracking on `*`; `strip_prefix`/`strip_suffix` remove the smallest or largest match. Not done: `[.x.]`, `[=x=]`, the pathname rules.
- **`shell.rs`**: `Shell` (owned by `Executor`) holds the shell's pgid, terminal fd, `is_interactive`, its saved terminal modes, the state of the special parameters (`name` = `$0`, `positional`, `last_status` = `$?`, `pid` = `$$` (kept by forked children), `last_async` = `$!`), the options (`options: BTreeSet<ShellOption>`, for `$-` and `set -o`; only state: `set_option` refuses any change, `Monitor` is on when interactive), the still unused `aliases`, `traps` and `hashed` tables, and `env: ShellEnv`: *all* shell variables (not only the exported ones) in a `BTreeMap` (sorted), initialised from the environment, which marks them exported. A `Var` is a `Value` (`Unset` or `Set(String)`; `Set("")` is null) plus independent attributes `VarAttr { exported, readonly }`; `Unset` with an attribute comes from `export X`/`readonly X`, `Unset` without one is never stored. Change variables through `assign` (keeps the attributes), `export`, `set_readonly`, `unset`: on a readonly variable they return a `ReadonlyError`, which the executor reports as a variable assignment error (`CommandError::Assignment` through `Executor::command_error`, or `Executor::fail`: exits a non-interactive shell, also for the prefixes of built-ins and programs). `parameter(&Parameter)` gives the value of a parameter, `None` when it is unset (a variable without a value, a position past `$#`, `$@`/`$*` without parameters, `$!` before any `&`). `exported()` gives the set, exported ones; `shell::quote` single-quotes a value for reinput. At startup (`Shell::new`, `init_variables`) `PWD` is kept from the environment only when it names the working directory without `.`/`..`, `PPID` and `OPTIND=1` are set, and `IFS` is reset to space, tab, newline. `Shell::with_env` builds a bare non-interactive shell, for tests. `Shell::new()` does the GNU-style interactive init: wait to be in the foreground, ignore job-control signals, `setpgid` itself (skipped when it already leads its group, e.g. as a session leader under `script`), grab the terminal. The terminal fd is a close-on-exec dup of stdin at fd >= 10, so children can still reach it in `pre_exec` after std replaced their stdin.
- **`builtin/`**: one module per built-in (with its synopsis and spec link), registered in the `BUILTINS` table (`name → FnBuiltin = fn(&mut Builtin) -> BuiltinResult`). `Builtin` carries stdin/stdout/stderr as trait objects, the argv (including the name) and `shell: &mut Shell`, so a built-in can change shell state (`cd` sets `PWD`/`OLDPWD`). The executor builds it and calls `builtin::run`, which handles the result like Rust handles `main`'s `Result`: an `Err` is reported on the built-in's stderr as `rush: <name>: <message>` and becomes the status (1, or the one of `Error::new(status, msg)`; 2 for clap usage errors, `--help` goes to stdout with 0), and stdout is flushed. Built-ins don't print their own errors or flush: they use `?` (`From` for `io::Error` → strerror text, `String`/`&str`, `clap::Error`), `.context(what)` on `io::Result`, and `bi.report(msg)` for a diagnostic after which they go on. Arguments are parsed with a `clap::Parser` struct through `bi.parse()?`, which applies the settings every built-in shares (`builtin::command`: the built-in's name in usage and errors, `--help` but no `-h`, repeated options allowed). Every built-in has such an `Args` struct (`pub(super)`), also the stubs and the ones that don't parse their arguments: its doc comment is the help text (first paragraph = the summary `help` lists, `override_usage` = the synopsis), kept in `BuiltinDef.command` and rendered by `builtin::help_command`. `builtin::run` prints it for `--help` as the first argument of any built-in. `Status` is `Exited(code)` or a request the executor carries out: `Eval(program)` (parse and run it in the current environment, `Executor::execute_str`), `Exec(argv)` (`Executor::exec`: replace the process, or with an empty argv keep the redirections; when exec fails the `RedirectGuard` puts the fds back), and `Exit(code)` (the executor flushes stdout and `_exit`s the current process: the shell, or the child of a pipeline command or subshell; not unwound yet, so no EXIT trap), and `Return`/`Break`/`Continue`, which are not unwound yet. Variable names are checked with `builtin::check_name` (`syntax::is_valid_name`), the `name[=word]` operands of `export`/`readonly` split by `builtin::declaration`, and their `-p` listings written by `builtin::print_declarations`; a `ReadonlyError` converts into an `Error` with `?`. `Builtin` also carries `jobs: &mut JobTable`; `jobs`/`fg`/`bg` take job IDs already parsed into `JobId` (`builtin::parse_job_id`, a clap `value_parser`), and the table never sees the strings. A built-in that needs the executor (shell code, the redirections, the `VAR=x` prefixes) returns such a variant instead of touching it. Outside a pipeline a built-in's redirections are applied to the shell process by a `RedirectGuard` (fds saved, applied, restored on drop; `exec` without a command keeps them, and a redirection targeting the terminal copy moves it first); inside one the forked child applies them for good. `BUILTINS` maps a name to a `BuiltinDef` (`Kind::Special` or `Kind::Regular`, POSIX §2.14), looked up with `builtin::find`. The `VAR=x` prefixes of a special built-in stay in the shell; a regular built-in's are set exported while it runs by a `TempVarsGuard` (`Shell::set_temporarily`; the built-in gets the guard as its `&mut Shell`, dropping it restores the variables). `builtin::run` returns `Err(status)` when the built-in returned an `Err`: for a special built-in that is a "special built-in utility error", which exits a non-interactive shell or forked child (`Executor::builtin_error`), as do a redirection error on one, a syntax error in `eval` and an `exec` that can't run its command. `bi.report` + `Ok(Status::FAILURE)` is a failure but not an error (the stubs use it, so they never exit a script). A built-in's stdin is a `nix::FdReader` on fd 0, never the buffered `io::stdin()`, which may hold script lines read ahead.
- **`job.rs`**: `Job` holds pids only (spawned programs and forked shells alike; a dropped `process::Child` neither waits nor kills), a per-pid `ProcStatus`, and the job's saved terminal modes (`tmodes`). Job-level state (`completed`, `stopped`, `completed_status`) is derived from the per-process statuses. `JobTable` (the executor's `jobs`) is a `BTreeMap` from job number to `JobEntry` (the `Job`, its command text, a `reported` flag): a new job gets the highest number + 1, the current/previous job (`+`/`-`) is the most recently used one with stopped jobs first, `find(&JobId)` resolves a job ID. Jobs are shown through a `JobReport` (`JobTable::report()`), a guard: `line(n, long)` gives the `jobs` line (`[1] + Stopped (SIGTSTP) sleep 30`) and marks the job reported, and dropping the report removes the reported jobs that completed. The command text is the AST printed back (`Display` for the syntax nodes). The shell reports jobs only with job control: `[n] <pid>` for `cmd &`, the `jobs` line when a foreground job stops (`Executor::job_stopped`) and, before each prompt, for background jobs that changed (`Executor::notify_jobs`, which then drops the completed ones). A non-interactive shell keeps completed jobs until `jobs` reports them.
- **`waiter.rs`**: job control; `Waiter<'s>` borrows the `Shell` (`wait`, `update_status`, `fg`, `bg`). Waiting consumes the `Job` and returns `WaitResult::Completed(JobExit)` or `WaitResult::Stopped { job, sig_stop }` (the stopped job is handed back for the job table). With job control it waits on the job's group with `WUNTRACED`; without (non-interactive, forked children) it waits each pid until it completes (`wait_completed`), because the jobs share the shell's group. In interactive mode, `wait` always hands the terminal back to the shell, even when waiting fails. A job's `tmodes` are saved when it stops and `take()`n when `fg` resumes it.

### Invariants to keep

- Children are reaped only through `nix::waitpid`. Never call `Child::wait()`/`try_wait()` on a job's children: they will already have been reaped and the call fails with `ECHILD`.
- With job control `waitpid` is called on the process group (`WaitPid::Group(pgid)`), so children must be in the job's process group; without job control (and in `update_status`) it is called per pid. Interactive: each pipeline gets its own group (`process_group`, the first command is the leader); foreground children take the terminal and reset the job-control signals to default in `pre_exec` (in that order: SIGTTOU must still be ignored for `tcsetpgrp`). Non-interactive: children stay in the shell's group and `job.pgid` is the shell's pgid.
- The shell must stay single-threaded: forked children (`fork_child`) run ordinary Rust code, which is only sound when no other thread could hold a lock at the fork. A forked child never returns to its caller (`catch_unwind` + `nix::_exit`), and the parent flushes stdout before forking.
- The status of every AST node is an `ExecStatus` (`executor.rs`); `ExecStatus::code()` gives `$?` (`128 + signum` for signals/stops). `failure()` is anything but `Exited(0)` (signals and stops included); an `interrupted()` lhs (SIGINT) stops an and-or list whatever the operator, and `not()` keeps it as is.
